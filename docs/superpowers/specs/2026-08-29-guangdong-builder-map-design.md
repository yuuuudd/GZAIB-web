# 广东高校共建者地图系统设计规格

- 项目：广州 AI 共创社
- 日期：2026-08-29
- 状态：产品与技术设计及书面规格均已确认
- 第一版定位：公开可浏览、审核后点亮、成员间双向同意连接的轻量平台

## 1. 背景与目标

广州 AI 共创社需要一个长期存在的跨校连接载体。它既不是单纯的地图打卡页，也不是第一天就具备动态、群聊和复杂关系链的社交产品。

第一版要完成四件事：

1. 让访客在广东地图上看见不同城市、学校和真实成员，直观感受到社区规模与活力。
2. 让访客通过地图进入成员资料，理解对方正在做什么、能够提供什么以及希望认识谁。
3. 让审核通过的成员无需运营人员转发，直接发送连接请求；双方同意后才交换联系方式。
4. 让真实贡献被记录和展示，使“共建者”身份来自行动而不是头衔。

产品原则：

- 看见人、了解人、连接人、记录真实共建。
- 地图服务于关系建立，不采集个人实时位置。
- 公开信息由本人逐项同意，未经审核不得发布。
- 正常连接不经过运营团队；运营只负责审核、安全与争议处理。
- 第一版保持轻量，不建设即时聊天、动态广场和复杂等级体系。

## 2. 用户与权限

### 2.1 访客

- 浏览广东共建者地图、学校聚合点和公开资料。
- 搜索与筛选学校、城市、能力方向和参与角色。
- 不能查看成员级资料，也不能发送连接请求。
- 可以提交加入申请。

### 2.2 申请人

- 通过邮箱一次性链接进入申请流程。
- 填写资料并为每类公开信息选择可见范围。
- 查看申请状态并在审核退回时修改资料。
- 审核通过前不出现在地图上。

### 2.3 已审核成员

- 使用邮箱一次性链接登录，无需设置密码。
- 查看其他成员的成员级资料。
- 发送、接受、婉拒、撤销连接请求。
- 管理自己的公开资料、联系方式、拉黑名单与通知。

### 2.4 认证共建者

- 拥有已审核成员的全部权限。
- 至少有一条经运营确认的真实贡献记录。
- 在地图和资料页显示橙色认证光环，不增加额外管理权限。

### 2.5 管理员

- 审核申请、学校坐标、资料修改和贡献记录。
- 隐藏、暂停或恢复成员资料。
- 处理举报并查看必要的安全审计信息。
- 不能代替成员接受连接请求，不能查看未被双方解锁的联系方式交换结果之外的私人意图。

## 3. 第一版范围

### 3.1 包含

- 广东高校地图、城市和学校聚合点。
- 头像点位、成员预览卡和完整资料页。
- 邮箱一次性链接登录。
- 申请点亮、逐项公开设置和运营审核。
- 普通成员与认证共建者双层身份。
- 公开贡献记录。
- 连接请求、接受、婉拒、撤销、拉黑和举报。
- 站内收件箱与邮件提醒。
- 运营审核后台和基本统计。
- 桌面端与移动端响应式体验。
- 地图不可用时的城市/学校列表降级页。

### 3.2 不包含

- 即时聊天、群聊和已读回执。
- 动态广场、点赞、关注和公开好友关系。
- 活动报名、项目协作和任务管理。
- 复杂积分、排行榜和多级头衔。
- 微信登录、公众号服务通知和小程序。
- 自动判断贡献真实性。
- 广东省以外的地图浏览。

## 4. 页面与导航

### 4.1 共建者地图首页

首屏以广东地图为主体，不使用通用后台式布局。

主要区域：

- 品牌导航：广州 AI 共创社、共建地图、活动、共建记录、关于我们。
- 价值主张：“让广东每一所高校，都亮起一束共建的光”。
- 主行动按钮：“申请点亮我的头像”。
- 搜索与筛选：城市、学校、关注方向、参与角色、认证状态。
- 广东地图、校园光点、头像聚合和成员预览卡。
- 高校数、成员数、城市数和近期新增成员统计。
- “提交资料—选择公开内容—运营审核—地图点亮”流程说明。

### 4.2 学校成员面板

- 展示学校/校区名称、城市、成员数量和主要方向。
- 桌面端从右侧展开；移动端使用底部抽屉。
- 展示该校成员头像、昵称、标签和身份状态。
- 支持在当前学校范围内继续筛选。

### 4.3 成员资料页

- 昵称、头像、学校、城市、专业与年级（按本人设置显示）。
- 一句话介绍与“我正在做什么”。
- “我能提供什么”和“我希望认识谁”。
- AI 方向、能力标签和参与角色。
- 已公开作品链接和贡献记录。
- 普通成员或认证共建者标识。
- “想认识 TA”按钮，以及拉黑/举报入口。

### 4.4 申请点亮页

- 邮箱验证与一次性登录链接。
- 个人资料、学校/校区、头像和能力方向。
- 每类资料的公开范围选择。
- 隐私说明、社区规则和明确同意。
- 提交成功、审核中、通过、退回修改和拒绝状态。

### 4.5 成员中心

- 修改资料和公开范围。
- 管理联系名片。
- 查看收到、发出和已完成的连接请求。
- 管理拉黑名单、通知设置和账号删除。
- 查看自己的贡献记录与认证状态。

### 4.6 运营后台

- 申请审核队列。
- 学校/校区与地图坐标管理。
- 贡献记录确认。
- 成员隐藏、暂停与恢复。
- 举报处理与操作审计。
- 成员、学校、城市和连接请求的汇总统计。

## 5. 地图体验

### 5.1 定位原则

- 只保存和显示学校/校区坐标。
- 不请求浏览器定位权限。
- 不采集住址、宿舍、实时位置或个人轨迹。
- 学校新增时由高德地理编码给出候选坐标，管理员确认后入库。

### 5.2 点位与聚合

- 一个成员关联一个学校/校区，不保存成员独立坐标。
- 地图缩放较远时按城市或距离聚合，显示人数和部分头像。
- 放大后显示校园光点；点击后展开该校成员。
- 最近七天加入的成员显示轻微蓝色呼吸光。
- 认证共建者显示橙色光环。
- 同一学校大量成员不在同一坐标叠放头像，而由学校面板展示完整列表。

### 5.3 社区连接感

- 经确认的跨校共同活动可以在相关学校之间显示短时连接线。
- 连接线代表公开的社区协作，不代表私人连接请求或联系人关系。
- 默认只展示近期公开活动形成的连接，避免地图长期过度拥挤。

### 5.4 降级体验

- 高德地图脚本或瓦片加载失败时，不阻断网站使用。
- 自动切换为按城市和学校分组的成员列表，保留搜索、筛选和资料访问。
- 记录地图加载异常用于排查，但不上传成员敏感信息。

## 6. 信息可见性

### 6.1 访客可见

- 昵称、头像、学校、城市。
- 一句话介绍。
- AI 方向、能力标签和参与角色。
- 本人选择公开的作品与贡献记录。

### 6.2 已审核成员可见

- 访客可见的全部资料。
- 更完整的个人介绍。
- “我能提供什么”。
- “我希望认识谁”。
- “想认识 TA”入口。

### 6.3 双方接受连接后可见

- 双方各自在联系名片中主动设置的微信、邮箱或其他联系方式。
- 任何一方删除联系名片或拉黑对方后，平台停止继续展示该联系名片。

### 6.4 仅本人和必要管理员可见

- 登录邮箱、审核材料、管理员备注、举报记录和账号状态。
- 真实姓名默认属于此层；只有本人主动切换公开范围后才进入公开资料。

## 7. 核心流程

### 7.1 申请与点亮

1. 申请人输入邮箱并获取一次性登录链接。
2. 系统验证链接为单次使用且未过期。
3. 申请人填写资料、选择学校并逐项设置可见范围。
4. 系统保存为待审核申请，地图不读取该数据。
5. 管理员审核并选择通过、退回修改或拒绝。
6. 通过后生成公开资料，头像在学校/校区光点中出现。
7. 成员收到站内通知和邮件结果。

### 7.2 认证共建者

1. 管理员创建或确认一条贡献记录。
2. 贡献记录包含活动、角色、成果、日期和公开说明。
3. 成员确认公开内容。
4. 成员拥有至少一条已确认贡献后，身份升级为认证共建者。
5. 若贡献记录被纠正，系统重新计算身份，不永久固化头衔。

### 7.3 连接请求

1. 已审核成员点击“想认识 TA”。
2. 系统要求填写不超过 500 字的自我介绍、连接原因和希望交流的话题。
3. 同一发送者每 24 小时最多发送 5 个新请求；同一成员对之间只能有一个待处理请求。
4. 接收者在站内收件箱看到请求，并收到邮件提醒。
5. 接收者选择接受或婉拒；发送者可以在处理前撤销。
6. 接受后，双方看到彼此当前联系名片；婉拒不暴露任何联系方式。
7. 任一方拉黑对方后，取消未处理请求并停止展示联系名片。

### 7.4 举报处理

1. 已审核成员从资料页或连接请求发起举报。
2. 系统保存举报类型、说明和必要的关联对象。
3. 管理员只查看处理举报所需的信息。
4. 管理员可以关闭举报、警告、暂停连接权限、隐藏资料或暂停账号。
5. 所有管理员处理动作写入审计记录。

## 8. 状态模型

### 8.1 申请状态

- `draft`：未提交。
- `pending`：待审核。
- `changes_requested`：退回修改。
- `approved`：已通过并可发布。
- `rejected`：拒绝。
- `withdrawn`：申请人撤回。

### 8.2 成员状态

- `active`：正常。
- `hidden`：本人或管理员隐藏公开资料，但保留登录和数据处理能力。
- `connection_suspended`：可以登录和查看，但不能发送连接请求。
- `suspended`：暂停登录和公开展示。
- `deleted`：完成删除流程，不再参与公开查询。

### 8.3 连接请求状态

- `pending`、`accepted`、`declined`、`withdrawn`、`cancelled_by_block`。

## 9. 数据模型

第一版采用关系型数据，主要实体如下：

- `users`：登录邮箱、角色、状态、最近登录时间。
- `magic_link_tokens`：令牌哈希、用途、过期时间和使用时间；原始令牌不入库。
- `applications`：申请内容、审核状态、提交时间和审核结果。
- `member_profiles`：昵称、头像、学校、介绍、方向、角色和发布状态。
- `profile_visibility`：每个可公开字段对应的访客/成员/私密可见级别。
- `schools`：学校、校区、城市、经纬度、坐标确认状态。
- `skills_and_interests`：统一标签及成员关联。
- `contributions`：活动、角色、成果、日期、确认状态和公开说明。
- `contact_cards`：微信、邮箱或其他联系渠道；字段加密存储。
- `connection_requests`：双方、请求内容、状态和处理时间。
- `blocks`：拉黑关系和时间。
- `reports`：举报对象、类型、说明与处理结果。
- `notifications`：站内通知、已读状态和邮件投递状态。
- `audit_logs`：管理员操作、目标对象、时间和必要差异摘要。

公开地图查询必须从已批准、处于正常发布状态且允许公开的资料视图中读取，不能直接读取申请表或私密资料表。

## 10. 系统架构

### 10.1 应用结构

- 响应式 Web 前端：地图、资料、申请、成员中心和后台界面。
- 服务端接口：鉴权、审核、公开资料、连接、安全与通知。
- 关系型数据库：成员、学校、贡献、连接和审计数据。
- 对象存储：头像原图和处理后的展示图。
- 邮件服务：登录、审核和连接提醒。
- 高德地图 JS API 2.0：地图、行政区域、地理编码和自定义点聚合。

### 10.2 推荐落地技术

- 网站：Sites 提供的 React/TypeScript 应用结构。
- 服务端：Cloudflare Worker 兼容的服务端接口。
- 数据库：D1。
- 头像存储：R2。
- 邮件：Resend HTTP API，通过通知适配层调用。
- 地图：高德地图 JS API 2.0、`AMap.MarkerCluster` 和 `AMap.Geocoder`。

### 10.3 模块边界

- `identity`：邮箱一次性登录、会话与角色。
- `applications`：申请、公开设置和审核。
- `directory`：公开资料、学校、标签、搜索和地图查询。
- `contributions`：贡献记录与共建者认证。
- `connections`：请求、状态、联系名片和限制。
- `safety`：拉黑、举报、暂停和审计。
- `notifications`：站内通知、邮件，以及未来公众号通知适配器。
- `admin`：只组合上述模块提供的管理能力，不复制业务规则。

## 11. 鉴权与安全

- 邮箱一次性登录链接有效期为 15 分钟、仅能使用一次。
- 数据库只保存令牌哈希，不保存可直接登录的原始令牌。
- 登录成功后使用安全、仅 HTTP、同站策略的会话 Cookie。
- 管理员账号使用独立允许名单，并记录所有高风险操作。
- 所有写操作校验会话、角色、资源归属和当前状态。
- 头像只允许常见图片格式，限制体积，重新编码后再公开提供。
- 连接请求按用户和目标成员限流，并拒绝重复待处理请求。
- 联系名片加密存储，只通过服务端授权接口读取。
- 高德安全密钥保存在服务端，通过代理方式接入，不写入公开前端代码。
- 公开接口不返回登录邮箱、联系方式、审核材料或内部标识。

## 12. 通知设计

第一版通知渠道为站内收件箱和邮件。

通知事件：

- 一次性登录链接。
- 申请提交、通过、退回修改或拒绝。
- 收到新的连接请求。
- 连接请求被接受、婉拒或撤销。
- 贡献记录被确认。
- 举报处理结果和账号状态变化。

邮件失败不回滚业务状态。站内通知始终保留，邮件投递状态单独记录，并允许系统有限次数重试。未来公众号服务通知接入同一通知模块，不改变申请和连接业务。

## 13. 异常与边界处理

- 地图失败：自动使用学校列表视图。
- 邮件失败：业务继续，站内通知可见，并显示重新发送入口。
- 头像失败：显示根据昵称生成的首字占位图。
- 学校坐标未确认：资料可审核但不能发布到地图，后台明确提示。
- 资料被隐藏或账号暂停：立即从公开查询中移除。
- 连接接受时任一账号不再正常：拒绝解锁联系方式并取消请求。
- 重复提交：写操作使用幂等键或状态校验，避免产生重复申请和请求。
- 删除账号：公开资料立即隐藏；活动审计信息只保留最小必要内容并去除公开身份关联。

## 14. 隐私与用户控制

- 申请时明确说明公开目的、字段、范围和连接机制。
- 用户可随时调整字段可见性，修改后立即影响公开查询。
- 用户可撤回申请、隐藏资料或申请删除账号。
- 联系方式不会出现在地图、搜索结果、公开资料或连接请求正文中。
- 不显示私人连接关系、连接数量或拒绝记录。
- 上线前必须发布与实际数据处理一致的隐私说明和社区规则。
- 产品默认执行最小公开原则；新增字段默认私密，必须由本人主动开放。

## 15. 响应式与可访问性

- 桌面端使用地图加右侧学校/成员面板。
- 移动端地图全屏，学校和成员信息使用底部抽屉。
- 地图中的所有成员与学校都可通过列表、键盘和搜索访问，不能只依赖拖拽地图。
- 头像、按钮、筛选和状态拥有文本标签与清晰焦点样式。
- 颜色不是区分普通成员与认证共建者的唯一方式，同时使用图标和文字。
- 动画遵循减少动态效果设置，呼吸光和连接线可以关闭。

## 16. 测试与验收

### 16.1 权限测试

- 待审核、拒绝、隐藏和暂停资料不出现在公开地图或搜索中。
- 访客不能获取成员级资料或发送连接请求。
- 已审核成员不能读取未接受连接的联系方式。
- 非管理员不能调用审核、暂停和审计接口。

### 16.2 核心流程测试

- 申请、退回修改、通过和点亮完整闭环。
- 贡献确认后共建者身份正确升级与回退。
- 连接请求发送、提醒、接受、婉拒、撤销和拉黑完整闭环。
- 修改公开范围后，地图、搜索和资料页立即一致。
- 删除或隐藏账号后，所有公开入口立即失效。

### 16.3 地图与界面测试

- 学校聚合、展开、搜索和筛选结果一致。
- 桌面、手机和触屏设备可完成全部核心流程。
- 模拟地图加载失败时，列表降级正常。
- 模拟头像和邮件失败时，页面与数据状态正确。
- 使用足量模拟学校和成员数据验证聚合性能与可读性。

### 16.4 上线门槛

- 构建通过，无阻断级错误。
- 权限矩阵和核心端到端流程全部通过。
- 高德生产密钥使用服务端保护方式。
- 邮件发送域名、隐私说明、社区规则和管理员名单已配置。
- 首批 10–20 位真实成员完成内测并确认公开资料无误。

## 17. 运营指标

第一版不以注册量作为唯一成功标准，重点观察：

- 被点亮的学校、城市和审核成员数量。
- 完整资料填写率与公开资料查看率。
- 连接请求发送率、接受率和举报率。
- 首次连接后继续参与活动或贡献的人数。
- 拥有真实贡献记录的认证共建者比例。
- 地图访问者进入成员资料页的比例。
- 资料被主动隐藏、修改公开范围和删除的情况。

这些指标只做汇总运营分析，不公开个人连接数量或社交排名。

## 18. 上线与演进

### 18.1 首批内测

- 运营团队先录入并邀请 10–20 位来自不同学校的真实成员。
- 每位成员确认自己的头像、学校、标签和公开范围。
- 完整演练申请审核、贡献确认和双向连接。
- 修复权限、隐私和移动端问题后再开放公开申请。

### 18.2 后续扩展顺序

1. 接入认证公众号服务通知。
2. 增加地图立体板块交互：点击头像后，其学校/城市区域以克制的地形板块方式抬升；当前 Demo 保持平面地图。
3. 增加活动发布与报名，但仍复用成员和贡献体系。
4. 评估是否需要简短站内回复；在没有真实需求前不建设完整聊天。
5. 当广东模式稳定后，再将地理范围扩展到其他省份。

## 19. 已确认的产品决策

- 资料经本人选择公开内容并由运营审核后点亮。
- 第一版使用专属一次性链接登录，不建设密码系统。
- 地图公开浏览，成员级资料和连接仅对已审核成员开放。
- 定位到学校/校区，不定位个人。
- 普通成员与认证共建者采用双层点亮。
- 连接请求直接发送给成员，不经过运营转发。
- 双方接受后才交换联系方式。
- 第一版使用站内收件箱与邮件提醒，公众号为后续扩展。
- 第一版采用轻量真实平台方案，不做完整校园社交网络。
